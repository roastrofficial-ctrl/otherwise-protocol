# Reference implementation boundaries

The reference is synthetic-only and independent of research/Cloud. The creator factory has a fixed laboratory message; custody enrollment rejects plaintext other than that exact synthetic value. There is no arbitrary-message CLI, real delivery integration, account authority, web UI or production deployment configuration. The fixed-content admission guard applies before ARM as a laboratory restriction, not as a new release predicate; portable verifiers do not impose it on archived payloads.

Python separates codec, crypto, object/lifecycle replay, clock/storage, client, backup demonstration and transport modules. The PHP verifier independently parses JSON (including duplicate keys), canonicalizes, computes commitments, checks signatures, replays lifecycle and opens recipient material. It does not execute Python. Both invoke Sodium's published main-subgroup validation workaround because older `crypto_core_ed25519_is_valid_point` releases alone can accept mixed-order points. Source: [Sodium point-validation documentation](https://libsodium.gitbook.io/doc/advanced/point-arithmetic). The reference requires 64-bit PHP for its exact safe-integer range. PHP uses ext-sodium, OpenSSL and an FFI binding to native Sodium point-validation APIs; FFI must be enabled for this command-line reference. This is a practical integration requirement, not an added trust authority or a reason to relax signature validation.

SQLite uses WAL and `synchronous=FULL`. One Capsule state BLOB contains descriptor, ciphertext, key and events. RELEASE writes the updated state and exact canonical archive/ciphertext BLOB in the same transaction, before returning anything. Both blobs carry corruption checksums; these are not anti-malicious-operator commitments. All operations serialize with `BEGIN IMMEDIATE`. Idempotency is reconstructed from the retained accepted commands; terminal export returns stored bytes without resealing. SQL storage is not normative wire semantics.

Known malformed/checksum-inconsistent stored material fails with `STORAGE_INTEGRITY`. Missing authority fails with `STORAGE_UNAVAILABLE`; the service never implicitly initializes a replacement. These are reference operational diagnostics, not signed evidence or new release predicates. Explicit laboratory initialization creates fresh keys; it does not gain authority over Capsules pinned to the old keys. The stored identity must agree with each loaded descriptor before further operation.

The default real clock starts unqualified after process construction. Time-dependent actions require an operator-qualified source; tests and the standalone example explicitly use a controlled synthetic clock. No HTTP clock-reset/fault endpoint exists. The HTTPS service is a loopback test server with caller-supplied test TLS material; it is not a production server or PKI. File/stdin transport runs the custodian in a separate local process and has different confidentiality, administration and timing assumptions.

Backups are unencrypted, labelled synthetic JSON files with mode 0600. The demonstration deletes working key files and restores originals from a separate temporary directory. This is deliberately not a production key vault or secure-erasure demonstration. A shared filesystem/host administrator can access the laboratory identities and custody keys.

The standalone client reconciles signed history before mutation, retains pending command bytes before sending, verifies that a receipt matches the exact requested command and valid prefix, and persists the result before acknowledging it. Interrupted replies remain unconfirmed. Retrying an accepted pending request recovers its original receipt rather than extending a lease twice. A verified newer prefix can invalidate an unaccepted pending CHECKIN basis; a newly signed command then needs a new request ID.

Corpus generation uses deterministic fixture-only material, including a documented Sodium sealed-box construction with fixed ephemeral fixture keys. Production primitive helpers always use their library's random ephemeral generation. Both generation paths are separate; fixture material is never used by CLI creation. The fixture generator declares expected outcomes from the specification and incorporates an independent PHP-produced release package.

The alpha pins image digests, Python wheel hashes and exact Debian downloads. See [Building](BUILDING.md) for reproduction scope and upstream-availability limits. This does not establish supply-chain security. Process-kill and torn-uncommitted-WAL tests do not establish physical power-loss survival, device fsync honesty, objective UTC or production service availability.
